Your AI Design Pipeline Needs a Router, Not a Bigger Prompt

Single-agent design workflows hit a ceiling fast. Here's the multi-agent architecture we built, what broke, and what actually works for production design systems.

Last quarter, we watched our single-agent design pipeline collapse in slow motion. One Claude instance was handling everything — token generation, component architecture, accessibility audits, and visual QA. It worked beautifully for the first dozen components. Then we asked it to refactor a 40-variant button system across three breakpoints and two themes. The context window choked. The output regressed. We spent three days cleaning up CSS that an agent had generated in twenty minutes.

That failure taught us something obvious in retrospect: a single LLM, no matter how capable, is a bottleneck. Not because it's stupid, but because it's forced to hold too many abstractions in working memory. Design systems are inherently multi-domain — color theory, layout logic, accessibility rules, animation physics, responsive behavior — and no single prompt can give an agent enough specialized depth across all of them.

The answer isn't a bigger context window. It's not better prompting. It's architecture.

The Ceiling of Single-Agent Design

Most teams start where we did: one agent, one task, iterate until it works. This pattern fails predictably at three thresholds:

  • Complexity threshold — When a component has more than ~8 interactive states or variants, the agent begins to drop edge cases. A button with default, hover, active, disabled, loading, and three size variants is manageable. Add a ghost variant, an icon-only mode, and dark-theme overrides, and the agent starts omitting states.
  • Cross-file threshold — Agents excel at generating isolated files. Ask one to update a token, regenerate the component, and fix the Storybook story that broke — tasks that require reasoning across three files with different conventions — and coherence drops sharply.
  • Quality threshold — A generalist agent generating CSS is not the same as an agent that has seen every WCAG 2.1 failure mode. When we ran our generated components through axe-core, single-agent output averaged 2.3 violations per component. Specialist agents brought that to zero.

The natural response is to chain agents: one generates tokens, one generates components, one audits. But chains are just sequential single-agent workflows with handoffs. The real gains come from orchestration: parallel agents with explicit roles, a shared state layer, and a router that delegates based on task type.

The Architecture That Survived

After six weeks of experimentation, we landed on a four-agent router pattern. Each agent is a specialist. None is generalist. A router — a lightweight classifier, sometimes another LLM, sometimes a rules engine — inspects incoming tasks and dispatches them.

# router.py — task classification before dispatch
def route_task(task: Task) -> Agent:
  if task.domain == "tokens":
    return token_agent  # DESIGN.md -> CSS custom properties
  elif task.domain == "components":
    return component_agent  # Token-aware component generation
  elif task.domain == "accessibility":
    return a11y_agent  # axe-core, color contrast, keyboard nav
  elif task.domain == "visual-qa":
    return qa_agent  # Screenshot diff, layout regression
  else:
    return review_panel  # Multi-agent debate for ambiguity

The critical insight: agents don't talk to each other directly. They read from and write to a shared state store. In our case, a simple JSON state file that lives alongside the codebase. Each agent sees only the state it needs, writes only what it's responsible for, and never has to parse another agent's natural language output.

Agent 1: The Token Architect

This agent owns the single source of truth: the token file. It doesn't generate components. It doesn't write documentation. It ensures that every hex code, spacing value, and radius has a semantic name and a documented rationale. When a designer requests a new "warning orange," the token agent evaluates contrast ratios against the existing palette, suggests a name like --color-semantic-warning, and appends it to the token file. Other agents pick it up automatically on their next run.

Agent 2: The Component Builder

The component agent reads the token file as its vocabulary. Its system prompt is short and rigid: "You may only use tokens from tokens.css. You may not invent values. You must output semantic BEM class names." Constraint, not creativity, is what makes this agent reliable. It generates the component markup and CSS, writes the file, and updates the state store with a manifest entry.

Agent 3: The Accessibility Auditor

This agent doesn't generate anything. It audits. It receives the component file path, lints it with axe-core, checks color contrast against the token values, and verifies keyboard navigation patterns. If it finds violations, it writes structured feedback to the state store — not prose, but machine-readable fix instructions. The component agent picks up those instructions and regenerates.

Agent 4: The Visual QA Agent

Our most experimental agent. It renders the component in a headless browser, captures a screenshot, and compares it against a reference baseline using pixel-diff. It catches the subtle regressions that code linters miss: a 1px misalignment, a color that shifted because a token was renamed, a hover state that no longer triggers. When it finds a diff, it files a visual regression report in the state store.

What Broke (And How We Fixed It)

This architecture didn't emerge fully formed. We broke it repeatedly.

Failure 1: State store conflicts. Two agents writing to the same key simultaneously corrupted our JSON state. The fix was versioning. Every write appends a timestamped entry. Agents read the latest version. On conflict, the router triggers a review panel — all four agents receive the conflicting entries and vote on resolution.

Failure 2: Agent drift. Over time, each agent's "understanding" of the codebase diverged. The token agent started naming things differently than the component agent expected. The fix was a weekly reconciliation job: each agent re-ingests the current state from scratch, dropping stale assumptions. It sounds expensive, but it's a 15-minute job that prevents multi-hour debugging.

Failure 3: Router brittleness. Our initial router was rule-based. It worked until it didn't — tasks that spanned domains ("redesign the nav with better contrast and new tokens") fell through the cracks. We replaced it with a lightweight classifier LLM that scores task descriptions against agent capabilities and can split multi-domain tasks into subtasks. One task becomes three parallel jobs.

Failure 4: The human bottleneck. With four agents generating and auditing, the volume of output overwhelmed our review capacity. We solved this by teaching the accessibility and visual QA agents to auto-merge trivial fixes — contrast tweaks, spacing corrections — and only surface structural changes for human review.

The Tools That Actually Matter

The orchestration space is noisy. CrewAI, AutoGen, LangGraph, Pydantic-AI, each promising to solve multi-agent coordination. We've tried most of them. Here's what stuck:

  • MCP servers — Not a framework, a protocol. Anthropic's Model Context Protocol let us expose our design token system, component registry, and visual regression store as standard tool endpoints. Any agent that speaks MCP can use them. We switched from custom APIs to MCP and cut integration time by 80%.
  • Pydantic-AI — For the router and individual agents, Python's type-safe agent framework gave us structured output validation without the overhead of LangGraph's graph DSL. It doesn't force a graph structure when you don't need one.
  • Playwright + pixelmatch — For visual QA. Headless browser rendering, screenshot capture, diff against baseline. Simple, fast, and the agent can understand the output because it's an image, not a DOM tree.
  • Git as state store — Not literally, but conceptually. Every agent change is a commit. The commit history is the audit trail. Rollback is a revert. We abandoned JSON state files in favor of committing directly to branches that agents own.

What We Gained

The numbers are stark. Single-agent workflow: ~20 minutes per component, 60% first-pass success, 2.3 a11y violations per component, 3 hours of human cleanup per day. Four-agent orchestration: ~35 minutes per component end-to-end, 94% first-pass success, zero a11y violations, and 20 minutes of human review per day.

The component takes longer because four agents run sequentially. But total human time dropped by 90%. The team reviews, approves, and merges. The agents handle generation, testing, and iteration.

The Takeaway

Design engineering in 2026 is not about finding the best single AI tool. It's about composing the right team of specialist agents and giving them a clean contract for collaboration. The router pattern, shared state, and strict output schemas matter more than model choice. A Claude 4 with a 200k context window will still fail at cross-file refactoring. Four GPT-4o-class agents with narrow scopes and a solid router will not.

If you're building with AI agents today, stop trying to make one agent smarter. Make your system decompose better. The intelligence is in the architecture, not the prompt.

We Stopped Writing Design Specs and Started Writing Agent Schemas — Here's the Difference

For six years, our design team wrote specs in Notion. Spacing rules, color usage, component anatomy — all in prose, with screenshots, with "do not" sections, with human context. Then we handed them to agents, and the agents ignored half of it. Not because they couldn't read. Because we were writing for the wrong consumer.

Every design team has a version of this document: a Notion page, a Confluence space, or a PDF called "Design System v3.2." It contains the accumulated wisdom of dozens of design decisions, written in the voice of a patient mentor. "Use this button sparingly for the primary action." "The card shadow should feel light, never heavy." "This color communicates warmth and approachability, not urgency." These specs are excellent at transferring design culture to new hires. They are terrible at directing AI agents.

The problem is not that agents are bad at reading. It's that design specs are optimized for human judgment, not mechanical execution. An agent reading "use sparingly" does not know what "sparingly" means. It knows what an enum is. It knows what a default is. It knows what validation failure is. And if your design system cannot be expressed in those terms, your agents will invent their own interpretation — which is exactly how you end up with a button that looks reasonable but violates every usage rule you have.

The Notion Problem

We learned this at scale when our agent committee started generating actual production components from design direction. We gave them a Notion link to our button spec, which was 14 paragraphs of guidance on usage, tone, hierarchy, and placement. The agents generated a button that was pixel-perfect in isolation but wrong in context. It used the primary variant for a secondary action. It placed a destructive action button next to a primary without the required separation. It chose the correct color but applied it to a hover state that our spec specifically called out as risky.

The agents were not hallucinating. They were doing exactly what a language model does: they were reasoning from pattern, not from rule. The spec said "primary buttons should be used for the main action." That is advice. An agent cannot validate against advice. It can only validate against constraints. And when the constraint layer is missing, the agent fills the gap with statistical probability — which is another way of saying it guesses.

What a Schema Actually Is

A JSON Schema is not a shorter design spec. It is a different category of document entirely. Where a spec says "you should do this," a schema says "these are the only values this system will accept." It is not guidance. It is a gate. And agents need gates, not guidance, because agents are not junior designers who learn over time. They are execution engines that need to know the boundaries before they start.

We re-wrote our core button, card, and input components as JSON Schema. Each schema defines:

Available properties and their types. No more guessing whether an icon should be string or boolean. The schema says icon: { type: "string", enum: [...] } and the agent knows exactly what it can pass.

Conditional logic. Our old spec said "avoid destructive buttons in modal contexts." Our schema says: if context is "modal", then variant cannot be "destructive". This is not a suggestion. This is a generation-time failure that forces the agent to retry with a valid option.

Default values for uncertain states. When an agent is unsure what variant to use, the schema provides a default — usually the safest choice. This eliminates the "primary button everywhere" problem that happens when agents default to what they see most often in training data.

Validation rules. A schema can specify that size only accepts ["sm", "md", "lg"]. If the agent generates "xl", the validator rejects it before anything reaches a browser. The error is specific, not a visual review comment with a red arrow in Figma.

The impact was immediate and measurable. Before schemas, our agent-generated components had about a 40% design review acceptance rate. After schemas, it hit 85%. The agents did not get smarter. The constraints got sharper. And sharp constraints are the only thing that makes agent-generated work reliable.

An Example of the Difference

Here is our card component, expressed in the two formats. The Notion spec said:

Cards should have a consistent shadow that creates depth without feeling heavy. Use shadow-lg for standard cards, shadow-md for nested cards, and avoid shadow on cards inside modals. The card background should always be surface-white, except in dark mode where it shifts to surface-900. Border radius is consistent at 12px, but nested cards should use 8px to show visual hierarchy.

Here is the same component as a schema, the way our agent committee now consumes it: 

{
  "type": "object",
  "properties": {
    "shadow": {
      "type": "string",
      "enum": ["shadow-sm", "shadow-md", "shadow-lg"]
    },
    "background": {
      "type": "string",
      "description": "Resolved at runtime based on theme"
    },
    "radius": {
      "type": "integer",
      "enum": [8, 12],
      "default": 12
    }
  },
  "if": {
    "properties": { "context": { "const": "modal" } }
  },
  "then": {
    "properties": { "shadow": { "const": "shadow-sm" } }
  },
  "if": {
    "properties": { "nesting": { "const": true } }
  },
  "then": {
    "properties": { "radius": { "const": 8 } }
  }
}

The schema does not explain why the shadow should be small in a modal. It makes it impossible to choose otherwise. An agent cannot generate a card with a heavy shadow inside a modal, because the schema simply does not allow that combination to exist. This is how you move from "hoping the agent follows the rules" to "knowing the agent cannot break them."

The Maintenance Trap

Converting specs to schemas is not free. It took us roughly two full days per major component to write, validate, and test. And schemas are not a one-time investment. They rot quickly. When your design team changes a border radius in Figma but forgets to update the schema, the next agent generation will produce legacy work. The schema and the visual system must stay in sync, or one becomes a lie.

We solved this by making the schema the source of truth. Not Figma. Not Storybook. The schema. Our design team now opens a pull request to update the JSON Schema, and the visual changes are reviewed in the same PR. Storybook and Figma are downstream consumers. This is backwards for most organizations, where Figma is the source. But if agents are part of your production pipeline, the machine-readable contract is the only source that agents can actually consume. It has to be canonical.

This means our design system is now more rigid than it was before. We lost some of the fluidity that comes with human interpretation. An expert designer cannot bend the rules for a compelling exceptional case — at least not without updating the schema. But we gained something more valuable: agents that generate exactly what we expect, every time. In a world where design work is increasingly automated, consistency is more important than creative latitude in the system layer. The creative latitude belongs in the product, not the system.

What Changed in Our Workflow

Four things are structurally different now. First, we write schemas first, then prose. The human-readable explanation lives in the schema's description field, but the validation logic is the primary document. Second, design reviews are shorter. We spend less time checking if the agent got the spec right, and more time evaluating whether the design intent is good. The "is it correct" question is now answered by a validator, not by a human eye.

Third, agent failures are fast and informative. When a generation fails, the error says "button.size is 'xl' but only ['sm', 'md', 'lg'] are allowed." This is infinitely more useful than a screenshot with a red circle and a Slack thread that says "this is too big." And fourth, our design system is more consistent because consistency is enforced, not encouraged. Encouragement works on humans. Enforcement works on machines.

The design system of the future is not a document you read. It is a contract you query, and the machine is a first-class citizen at the table.

Convert your design specs to JSON Schema for the components your agents touch. Start with your ten most-used components — button, card, input, modal, table. The goal is not to eliminate design review, but to move it from compliance checking to quality evaluation. Agents will follow rules that are written to be followed. Prose is for humans. Schemas are for machines. Write for both, and let each do what they're best at.
